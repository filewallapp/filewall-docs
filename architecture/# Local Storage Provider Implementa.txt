# Local Storage Provider Implementation Walkthrough

I have successfully implemented the Local Storage provider as a first-class production backend, adhering perfectly to your architectural guidance. The API layer is now completely provider-agnostic, and both the frontend and worker environments interact seamlessly with local storage when configured.

Here is a breakdown of the implementation:

## 1. Environment Configuration

- Updated both `/web/.env.example` and `/worker/.env.example` to include the new configuration keys:
  ```env
  # Storage Provider (local or r2)
  STORAGE_PROVIDER=local
  LOCAL_STORAGE_PATH=/storage
  ```

## 2. Shared Web Storage Abstraction

The Next.js application has been fully refactored to consume a centralized storage abstraction.

- **Types Extracted**: Extracted `FileStorage` and its related types out of `r2.ts` into `types.ts`.
- **R2 Storage**: Refactored `r2.ts` to implement the `FileStorage` interface without altering any of its existing Cloudflare logic.
- **Local Storage Provider (`local.ts`)**: Implemented the `FileStorage` interface using native Node.js `fs/promises`.
  - Core methods (`getFile`, `uploadFile`, `copyFile`) read and write directly to `LOCAL_STORAGE_PATH`.
  - `getPresignedPutObjectUrl` and `getPresignedGetObjectUrl` now generate **temporary authenticated application URLs** pointing to the generic `/api/storage/[action]` endpoint. These URLs are signed using HMAC-SHA256 based on `PROJECT_SHARE_SIGNING_SECRET`.
- **Singleton Abstraction (`index.ts`)**: Created the `storage` singleton that dynamically instantiates either `LocalStorage` or `R2Storage` based on `process.env.STORAGE_PROVIDER`.
- **Provider-Agnostic Consumption**: Updated `FileService` to consume the `storage` singleton instead of `r2Storage` directly.

## 3. Generic Storage API Route

Implemented the provider-agnostic `/api/storage/[action]/route.ts` API endpoint.

- Serves as the central ingestion and extraction point for the frontend when Local Storage is active.
- Handles `GET` (for `download`) and `PUT` (for `upload` and `upload-part`).
- Strictly verifies HMAC signatures generated by the `LocalStorage` provider to prevent unauthorized access.
- Simply proxies valid requests down to the generic `storage` singleton, ensuring the API route itself has no underlying knowledge of the active provider.

## 4. Worker Storage Abstraction

The worker has also been refactored to support seamless, network-free local storage interactions.

- **Generalized Storage Layer (`utils/storage.ts`)**: Created a new storage module exporting `headObject`, `downloadObject`, `uploadObject`, and `uploadJsonObject`.
  - When `STORAGE_PROVIDER=local`, these methods interact **directly** with the `LOCAL_STORAGE_PATH` via the filesystem (`fs.copyFile`, `fs.writeFile`), bypassing the HTTP network overhead entirely.
  - When `STORAGE_PROVIDER=r2`, they fallback to the existing `utils/r2.ts` methods.
- **Handler Updates**: Updated `src/worker/handler.ts` to consume the generalized methods instead of R2-specific ones.
- **Admin & HTTP Servers**: Refactored `admin.ts` to perform stuck job recovery logically based on the presence of a generic `hasStorageSource`, and modified `http.ts` to skip `R2_PUBLIC_BASE_URL` checks when using local storage.

## 5. Documentation

Created a comprehensive `LOCAL_STORAGE_SETUP.md` guide at the root of the project. It explicitly documents Local Storage as a production feature, details how the architecture works, and includes a sample Docker Compose configuration demonstrating the shared volume mount across `/web` and `/worker`.

## Verification

- Ran the TypeScript compiler (`pnpm tsc --noEmit`) on both `/web` and `/worker`. All type mismatches and interface errors (including those caused by strict Next.js 15 route signatures) were resolved, and the codebase compiles cleanly!
